# AMS SITE CORE

**Версия:** 1  
**Статус:** базовая конституция AMS для сайтов  
**Модель работы:** владелец / архитектор + AI  
**Назначение:** лендинги, корпоративные сайты, сайты услуг, каталоги и сайты, которые при необходимости могут вырасти в приложение

---

## 0. Как использовать этот документ

Этот документ задаёт обязательные архитектурные правила.

Перед выполнением задачи AI должен определить:

1. какой тип проекта выполняется;
2. какие модули реально включены;
3. какие данные принадлежат сайту;
4. какие данные приходят извне;
5. какие правила URL и SEO уже опубликованы;
6. какие решения владельца проекта имеют приоритет;
7. что реально проверено, а что является предположением.

Если задача конфликтует с конституцией:

- не обходить правило молча;
- описать конфликт;
- предложить минимальное безопасное решение;
- не менять архитектурный контракт без решения владельца.

Если данных не хватает:

- ничего не придумывать;
- скрыть элемент, использовать безопасную нейтральную формулировку или `noindex`;
- зафиксировать блокер;
- продолжить работу там, где это безопасно.

Статусы утверждений:

- `VERIFIED` — реально проверено кодом, сборкой, тестом или достоверным источником;
- `HYPOTHESIS` — рабочее предположение;
- `REQUIRES CHECK` — требуется проверка.

Фразы «готово», «проверено», «работает» запрещены без фактической проверки.

## 1. Главный принцип

Сайт должен быть:

- самостоятельным;
- переносимым;
- понятным одному владельцу;
- удобным для разработки вместе с AI;
- SEO-полноценным;
- безопасным;
- минимально сложным;
- независимым от необязательных внешних сервисов.

Внешний сервис может поставлять данные, принимать заявки или выполнять отдельную функцию, но он не должен становиться владельцем сайта.

Сайт владеет:

- URL;
- SEO;
- canonical;
- sitemap;
- robots;
- текстами;
- юридическим контентом;
- дизайн-системой;
- навигацией;
- правилами индексации;
- формами;
- публичным поведением страниц.

Внешние системы поставляют факты или принимают данные через явный контракт.

---

## 2. Приоритет правил

При конфликте решений используется следующий порядок:

1. явное решение владельца;
2. опубликованные архитектурные решения проекта;
3. фактическое состояние кода, lockfile и production-конфигурации;
4. AMS SITE CORE;
5. активный отраслевой профиль;
6. активные модули;
7. проектные требования;
8. UI-конституция;
9. макеты и референсы;
10. текущая задача;
11. чат и память AI.

Активный отраслевой профиль может уточнять Core только там, где это явно обозначено.

Код, случайно нарушающий Core, не становится новым стандартом.

## 3. Уровни проектов

### L1 — лендинг

Обычно:

- одна основная страница;
- юридические страницы;
- 404;
- формы заявок.

### L2 — корпоративный сайт

Обычно:

- услуги;
- о компании;
- контакты;
- кейсы;
- статьи или журнал;
- формы.

### L3 — каталог

Дополнительно:

- сущности каталога;
- карточки;
- фильтры;
- детальные страницы;
- локальный или внешний источник данных.

### L4 — приложение

Только при доказанной необходимости:

- собственная БД;
- серверное состояние пользователя;
- личные кабинеты;
- роли;
- редакторы;
- заказы;
- оплаты;
- сложные фоновые процессы.

Переход между уровнями не должен сам по себе менять уже опубликованные URL, SEO-архитектуру и UI.

## 4. Модули

Модули включаются независимо друг от друга.

Базовые модули:

- `LEADS` — формы и заявки;
- `JOURNAL` — статьи и редакционный контент;
- `CATALOG` — сущности и каталог;
- `DATABASE` — собственная БД проекта;
- `ANALYTICS` — аналитика;
- `INDEXNOW` — уведомления поисковых систем.

Выключенный модуль:

- не создаёт маршруты;
- не создаёт ссылки;
- не попадает в sitemap;
- не тянет лишние зависимости.

Нельзя строить инфраструктуру «на будущее».

## 5. Hard Contract

### 5.1. Архитектура

1. Production-сайт работает как живой Next.js-сервер.
2. Статический export не является базовой production-моделью.
3. Server Components используются по умолчанию.
4. `"use client"` применяется только там, где действительно нужна интерактивность браузера.
5. Код разделён минимум на четыре ответственности: platform, project, ui, app/routes.
6. UI не знает, откуда получены данные.
7. Страница не читает БД, файлы, API или snapshot напрямую.
8. Данные проходят через Repository/Service-контракт.
9. Новая инфраструктура появляется только при доказанной необходимости.
10. Отдельный backend, Redis, очередь, поисковый движок или новая БД требуют отдельного архитектурного решения.

### 5.2. Владение

11. URL и SEO принадлежат сайту.
12. Тексты и юридический контент принадлежат проекту.
13. UI-система принадлежит проекту.
14. Внешний источник не определяет canonical и индексацию.
15. Внешний источник не должен быть обязательным для обычного рендера страницы, если проект использует локальный snapshot.

### 5.3. SEO

16. Внутренние ссылки, canonical, sitemap, breadcrumbs и redirects используют единый URL-builder.
17. Опубликованный URL не меняется молча.
18. Постоянный redirect по умолчанию — HTTP 308.
19. Неизвестный URL отдаёт 404.
20. Намеренно удалённая сущность может отдавать 410.
21. Массовый redirect удалённых страниц на главную запрещён.
22. Индексируется только явно разрешённая страница.
23. Техническая возможность открыть URL не означает право индексировать его.
24. Structured data строится только из реальных данных.
25. В непубличных окружениях индексация закрыта полностью.

### 5.4. Контент и факты

26. AI не придумывает цифры, цены, отзывы, рейтинги, сроки, ФИО, стаж, количество клиентов, гарантии и коммерческие преимущества.
27. Изменчивый факт хранится с источником и датой проверки.
28. Просроченный факт скрывается или заменяется формулировкой без конкретного числа.
29. Runtime-генерация маркетинговых текстов AI запрещена.

### 5.5. Безопасность

30. Секреты не попадают в Git, клиентский JavaScript, документацию и логи.
31. Персональные данные не передаются в аналитику.
32. Формы не публикуются без правового основания и страницы согласия.
33. Внешние origin работают по allowlist.
34. Wildcard-доступ к произвольным внешним хостам запрещён.
35. Сырой HTML из внешнего источника не выводится без безопасного renderer.
36. Уязвимая версия фреймворка не допускается в production.

### 5.6. Простота

37. Нет CMS без реальной потребности.
38. Нет БД без реальной потребности.
39. Нет универсального page builder без бизнес-задачи.
40. Нет абстракции, которая существует только «на всякий случай».
41. При одинаковой безопасности выбирается более простое решение.

Новая библиотека добавляется только если текущий стек не решает задачу разумно.

### platform

Общие механизмы:

- routing;
- SEO;
- формы;
- безопасность;
- данные;
- форматирование;
- аналитика;

В platform нет бренда, конкретного города, телефонов клиента, проектных текстов, проектных цветов и проектных URL-литералов.

Всё, что относится к конкретному проекту:

- навигация;
- SEO-реестр;
- тексты;
- тема;
- redirect-правила;
- флаги модулей;

Компоненты интерфейса: primitives, layout, shared, domain, sections.

Маршруты и композиция страниц.

Маршрут:

- разрешает URL;

## 8. Данные

### 8.1. Универсальная цепочка

```text
Source
→ Adapter
→ Repository
→ DTO / ViewModel
→ UI
```

UI не должен меняться при переходе:

```text
local data
→ snapshot provider
→ database
```

### 8.2. Режимы данных

Допустимые логические режимы:

- `none` — внешних данных нет;
- `local` — данные принадлежат проекту;
- `snapshot` — сайт получает версионированный локальный snapshot от внешнего поставщика;
- `db` — собственная БД проекта.

`db` включается только при доказанном триггере.

### 8.3. Snapshot как абстракция

Core не привязывает сайт к конкретному Data Hub.

Если используется `snapshot`:

- сайт зависит от контракта данных, а не от бренда поставщика;
- поставщика можно заменить;
- обычный page request не обращается к поставщику;
- последняя корректная версия данных хранится локально;
- плохое обновление не заменяет рабочее;
- смена поставщика не должна менять URL, SEO и UI.

Отраслевой профиль определяет конкретный snapshot-контракт.

## 9. Конфигурация

Конфигурация должна иметь один источник истины.

Минимальные режимы:

```text
INDEXING_MODE = private | staging | public
DATA_MODE     = none | local | snapshot | db
```

Модули включаются независимыми флагами.

Правила:

- безопасные значения используются по умолчанию;
- production-индексация включается только явно;
- env проверяется Zod-схемой;
- отсутствующий обязательный env останавливает запуск;
- секреты не имеют тихих fallback-значений.

## 10. URL

Для каждого класса страниц должен существовать канонический URL-builder.

Обязательные свойства:

```text
buildUrl(entity) → path
parseUrl(path) → entity
```

Для поддерживаемых маршрутов:

```text
parseUrl(buildUrl(x)) = x
```

Правила:

- URL lowercase;
- слова через дефис;
- единая транслитерация;
- ограниченная и понятная глубина;
- зарезервированные корни не конфликтуют с slug;
- literal URL в переиспользуемых UI-компонентах запрещены;
- canonical строится тем же владельцем URL.

Нормализация формата URL выполняется одним способом.

---

## 11. Redirect и жизненный цикл URL

Порядок обработки:

1. нормализация технического URL;
2. исторический permanent redirect;
3. migration redirect;
4. lifecycle redirect;
5. 410;
6. 404;
7. рендер существующей страницы;
8. решение об индексации.

Content Gate применяется только к существующей странице.

Постоянные redirects по умолчанию используют 308.

Redirect chains запрещены.

---

## 12. SEO Registry

Индексируемые страницы должны быть перечислены в SEO Registry.

Минимальная запись:

- page key;
- intent;
- canonical rule;
- title;
- description;
- H1;
- robots;
- Content Gate;
- OG rule.

Правила:

- один поисковый intent — один владелец;
- дубли intent запрещены;
- title и description должны быть осмысленными и уникальными;
- один H1;
- H2/H3 формируют логическую структуру;
- переменные подставляются только из фактов;
- если факта нет, используется формулировка без него.

Если для индексируемого маршрута отсутствует SEO-правило, production-проверка должна падать.

---

## 13. Content Gate

Страница индексируется только если одновременно:

- URL существует;
- lifecycle разрешает страницу;
- статус страницы разрешает индексацию;
- SEO Registry разрешает индексацию;
- контент достаточен;
- факты достаточно свежие;
- обязательные медиа присутствуют;
- `INDEXING_MODE=public`.

Если существующая страница не проходит Gate:

```text
HTTP 200
robots: noindex,follow
self canonical
не включать в sitemap
```

Временная нехватка контента не превращается в ложный 404.

---

## 14. Фильтры и пагинация

Индексируемые фильтры создаются только по whitelist.

Все произвольные query-комбинации:

- не считаются самостоятельными SEO-страницами;
- получают `noindex,follow`;
- не попадают в sitemap.

Для пагинации:

- `page=1` нормализуется к базовому URL;
- page 2+ имеет собственный URL;
- canonical page 2+ указывает на себя;
- политика индексации page 2+ задаётся проектом: `index` или `noindex`.

Core не навязывает один вариант для всех сайтов.

---

## 15. Sitemap и robots

Sitemap содержит только страницы, которые:

- canonical;
- возвращают 200;
- разрешены SEO Registry;
- проходят Content Gate;
- разрешены текущим окружением.

`lastmod` — только реальная дата изменения контента.

Дата сборки не используется как искусственный `lastmod`.

При `private` или `staging`:

- весь сайт `noindex`;
- crawling закрывается согласно политике окружения;
- публичный sitemap не публикует индексируемый набор.

Если sitemap или robots зависят от runtime-данных, они должны формироваться из текущего состояния, а не замораживаться на build-time.

---

## 16. Structured Data

Разметка строится только из фактов.

Запрещено генерировать:

- `AggregateRating` без реального рейтинга;
- `Review` без реальных отзывов;
- ложное наличие;
- фиктивные цены;
- фиктивную организационную информацию.

FAQ schema допускается только если FAQ реально виден пользователю.

---

## 17. Контент

Контент отделён от компонентов.

Компонент отвечает за представление.

Контент отвечает за тексты, заголовки, факты, legal и статьи.

Длинный редакционный контент хранится в удобном версионируемом формате, например Markdown/MDX.

Frontmatter валидируется.

Изменчивый факт должен поддерживать:

```text
value
source
checkedAt
expiresAt?
```

Если срок проверки истёк, факт скрывается либо текст перестраивается без него.

## 18. Формы и заявки

### 18.1. Базовый принцип

Заявка не должна теряться при кратком сбое CRM, webhook или внешнего lead-сервиса.

Используется один простой механизм:

```text
Form
→ server validation
→ anti-spam
→ consent check
→ durable local spool
→ delivery
→ ACK
→ remove from spool
```

### 18.2. Durable local spool

Spool:

- работает только если включены формы;
- хранится на persistent volume;
- не требует БД;
- не требует Redis;
- не требует отдельного брокера;
- использует атомарную запись;
- использует уникальный `leadId`;
- шифрует персональные данные at rest;
- не пишет ПД в application log.

Если запись в spool не удалась, заявка не считается принятой.

Если запись в spool удалась, сайт может подтвердить пользователю приём заявки, даже если внешний канал временно недоступен.

### 18.3. Маршрут заявки

Единая модель:

```text
LEADS_ROUTE = direct | service | dual
```

- `direct` — напрямую в канал клиента;
- `service` — во внешний lead-service;
- `dual` — в оба направления.

Канал direct:

```text
LEAD_TRANSPORT = none | smtp | webhook | crm
```

`none` разрешён только там, где отправка формы фактически отключена или тестируется.

Для `dual` каждая доставка имеет собственный статус ACK.

Lead удаляется из spool только после выполнения требуемой политики доставки.

По умолчанию для `dual` обе ветки должны подтвердить приём.

Если проекту нужна другая политика, она задаётся явно.

### 18.4. Retry

Повтор доставки:

- выполняется тем же приложением или лёгкой scheduled-задачей;
- не требует отдельной очереди;
- идемпотентен по `leadId`;
- использует ограниченный backoff;
- не создаёт дубли при повторном ACK.

Невозможность доставить заявку должна быть видна в health/operations, но не раскрывать ПД.

### 18.5. Поля заявки

В transport context допускаются только безопасные идентификаторы страницы и публичной сущности.

ПД:

- не передаются в URL;
- не попадают в аналитику;
- не попадают в обычные логи.

Срок хранения недоставленной заявки и политика удаления задаются проектом.

---

## 19. Аналитика и cookies

Аналитика:

- не влияет на работоспособность сайта;
- не влияет на форму;
- не получает ПД;
- учитывает согласие пользователя там, где оно требуется.

Session replay и Webvisor разрешаются только после проверки маскировки полей и правового основания.

События типизированы.

---

## 20. Медиа

Правила:

- использовать оптимизированные размеры изображений;
- задавать корректные `sizes`;
- фиксировать aspect ratio;
- приоритизировать только LCP-медиа;
- остальные медиа загружать лениво;
- иметь нейтральный fallback;
- внешний media origin разрешать только через allowlist.

Компоненты не должны зависеть от конкретного storage-provider.

---

## 21. Рендер и кэш

Статичные по смыслу страницы могут генерироваться статически.

Страницы с изменяемыми runtime-данными должны показывать актуальное локальное состояние.

ISR, `use cache`, reverse-proxy HTML cache и иные механизмы допускаются только если доказано, что они не нарушают:

- актуальность;
- lifecycle;
- Content Gate;
- sitemap;
- robots;
- пользовательские данные.

`/_next/static` и immutable assets кэшируются агрессивно.

POST, health, internal triggers и персонализированные ответы не кэшируются.

---

## 22. Безопасность

Минимум:

- CSP;
- HSTS;
- `X-Content-Type-Options`;
- `Referrer-Policy`;
- `Permissions-Policy`;
- запрет framing через CSP;
- rate limit на публичные API;
- allowlist внешних origin;
- SSRF-защита для серверных загрузок;
- секреты только server-side;
- логи без ПД и секретов;
- dependency audit;
- security-supported Next.js.

Внутренние endpoint:

- не доступны анонимно;
- не принимают произвольные URL;
- не возвращают приватные данные.

---

## 23. Производительность

Целевые Core Web Vitals на мобильных:

- LCP ≤ 2.5 s;
- CLS ≤ 0.1;
- INP ≤ 200 ms.

Это цели production-сборки, а не локального dev-сервера.

Правила:

- минимум клиентского JavaScript;
- client components только по необходимости;
- тяжёлые widgets загружаются лениво;
- шрифты подключаются централизованно;
- не грузить невидимые галереи и карты заранее.

---

## 24. Обязательные состояния сайта

Каждый production-проект должен иметь:

- 404;
- error boundary;
- controlled loading/error states;
- юридические страницы, если собираются ПД;
- consent для обработки ПД, если есть формы;
- корректное состояние успешной отправки;
- корректное состояние ошибки;
- health endpoint без секретов.

---

## 25. Окружения

### local

- разработка;
- индексация закрыта.

### staging

- проверка;
- индексация закрыта;
- при необходимости доступ дополнительно ограничен.

### production

- публичная индексация включается только после решения владельца;
- все проверки и legal готовы.

---

## 26. Production

Базовая production-модель:

```text
Git / CI
→ Docker image
→ VPS / container runtime
→ reverse proxy
→ Next.js server
→ persistent volume при необходимости
```

Для standalone-сборки Next.js используется сгенерированный standalone server.

Контейнер:

- multi-stage;
- запускается не от root;
- не содержит dev-зависимости без необходимости;
- имеет healthcheck;
- не хранит изменяемые production-данные внутри эфемерного слоя образа.

Rollback кода выполняется предыдущим проверенным image.

---

## 27. Переносимость

Сайт не должен быть технологически заложником AMS или внешнего сервиса.

Передача должна быть возможна при наличии:

- исходного кода;
- lockfile;
- публичных контрактов;
- project config;
- контента;
- локальных данных или exit snapshot;
- медиа клиента;
- прямого канала заявок;
- инструкции запуска.

Production-сборка не должна зависеть от приватного пакета, который невозможно передать клиенту.

---

## 28. Триггеры собственной БД

БД оправдана, если появляется хотя бы одно:

- клиент сам изменяет данные через админку;
- несколько редакторов;
- роли и согласования;
- серверное состояние пользователя;
- личный кабинет;
- корзина;
- заказ;
- оплата;
- локальные изменяемые данные, которых нет во внешнем источнике;
- надёжная сложная очередь, которую простой spool уже не покрывает.

Даже после подключения БД:

- URL не меняются;
- SEO не меняет владельца;
- UI получает те же DTO;
- Repository скрывает источник.

---

## 29. Что не строить

Без доказанного триггера запрещены:

- CMS;
- админка;
- ORM;
- БД;
- Redis;
- Kafka/RabbitMQ;
- Elasticsearch;
- Meilisearch;
- микросервисы;
- Kubernetes;
- второй backend;
- универсальный page builder;
- вторая UI-библиотека;
- инфраструктура «может пригодиться».

---

## 30. Проверки

Проект должен иметь автоматизируемые проверки минимум для:

- lint;
- TypeScript;
- production build;
- архитектурных границ;
- URL;
- redirects;
- SEO Registry;
- canonical;
- sitemap;
- robots;
- structured data;
- security;
- forms;
- durable lead spool;
- data contracts;
- performance smoke;
- e2e smoke.

Проверка считается пройденной только если команда реально запускалась.

---

## 31. Git и AI-процесс

Правила:

- работа идёт небольшими проверяемыми изменениями;
- одна архитектурная задача не смешивается с несвязанным рефакторингом;
- изменение Hard Contract фиксируется как архитектурное решение;
- перед merge выполняются обязательные проверки;
- AI сообщает, что именно реально проверил.

Отчёт AI после задачи:

```text
СДЕЛАНО
ИЗМЕНЕНО
ИСПОЛЬЗОВАНО ПОВТОРНО
ДОБАВЛЕНЫ ЗАВИСИМОСТИ И ПОЧЕМУ
ИЗМЕНЕНЫ КОНТРАКТЫ
РЕАЛЬНО ПРОВЕРЕНО
НЕ ПРОВЕРЕНО
БЛОКЕРЫ
```

---

## 32. Definition of Done

Эпик или проект не считается готовым, пока:

- production build не проходит;
- обязательные проверки не проходят;
- URL централизованы;
- SEO Registry согласован;
- canonical корректен;
- robots и sitemap соответствуют окружению;
- Content Gate работает;
- 404/410/redirect не конфликтуют;
- форма не теряет принятую заявку при кратком сбое внешнего канала;
- spool не пишет ПД в лог;
- legal готов;
- секретов нет в коде;
- UI соответствует UI-конституции;
- нет выдуманных фактов;
- проект можно развернуть без скрытых ручных зависимостей.

---

## 33. Финальный принцип

```text
Простой сайт должен оставаться простым.

Сложность разрешена только там,
где она защищает данные,
SEO,
заявки,
безопасность
или реальную бизнес-функцию.
```

Архитектура AMS строится так, чтобы сайт можно было развивать, менять поставщиков данных и интеграций, передавать другому подрядчику и масштабировать без переписывания публичной части.
